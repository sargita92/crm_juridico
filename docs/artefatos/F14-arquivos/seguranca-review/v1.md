# Análise de Segurança — F14 Arquivos por Lead

## Resultado: **APROVADO com observações**

## Ameaças avaliadas (OWASP Top 10 aplicáveis)

### A01 — Broken Access Control

| Vetor | Proteção implementada | Evidência |
|-------|----------------------|-----------|
| Acesso anônimo | Middleware `auth` aborta com 401 em todas as rotas | [owasp_test.go](../../../../internal/files/interfaces/http/owasp_test.go) · `TestOWASP_Unauthenticated_Returns401` |
| Usuário sem permissão | Middleware `requirePerm("files", "view")` aborta com 403 | idem, `TestOWASP_InsufficientPermission_Returns403` |
| Cross-tenant file ID | `FindByID` filtra por `tenant_id` no SQL; handler retorna **404** (não 403) para não vazar existência | `TestHandler_PreviewDrawer_CrossTenant_404`, `TestHandler_Download_CrossTenant_404` |
| Cross-tenant lead filter | `LeadFilter` também filtra por `tenant_id`; lead de outro tenant retorna lista vazia | `TestGormFileRepository_List_TenantIsolation` |

**Avaliação: OK.** Isolamento é verificado em SQL e no handler. Não há path onde o `tenant_id` fica implícito.

### A03 — Injection

| Vetor | Proteção | Evidência |
|-------|----------|-----------|
| SQL injection via params | Gorm usa prepared statements; todas as queries recebem `?` placeholders | código de `GormFileRepository` |
| LIKE pattern injection | `escapeLike` escapa `%`, `_`, `\` antes de concatenar; cláusula usa `ESCAPE '\\'` | `TestGormFileRepository_List_SearchEscapesLikeWildcards` |
| Path traversal no storage | `LocalDiskStorage.resolve` refuse chaves com `..`, `/absolute`, ou fora da raiz; `SanitizeFileName` + UUID como `storage_key` | `TestLocalDiskStorage_PathTraversalBlocked`, `TestSanitizeFileName` |

**Avaliação: OK.** Sanitização é feita na camada de domínio (nome) e infraestrutura (chave). A chave nunca é controlada pelo atacante — é um UUID gerado pelo use case.

### A04 — Insecure Design

- **Tamanho máximo configurável** (`FILES_MAX_BYTES`, default 50 MB) → `TestStoreFileUseCase_RejectsOversizedContent`.
- **Captura best-effort**: falha de storage não derruba ingestão da mensagem, mas gera log `error`.
- **Lead opcional**: se a mídia chega antes do lead existir, persiste com `lead_id=NULL` (não trava).

### A05 — Security Misconfiguration

| Risco | Mitigação |
|-------|-----------|
| MIME sniffing no browser | Header `X-Content-Type-Options: nosniff` em Download e Thumbnail |
| Cache em proxy público | `Cache-Control: private, max-age=0, no-cache` no download; `private, max-age=300` em thumbnails (TTL curto aceitável pois a URL requer auth) |
| Polyglot inline | `Thumbnail` serve **apenas** `media_type == image` — qualquer outro tipo retorna 404 |
| Conteúdo executável inline | `Content-Disposition: attachment` força download mesmo para HTML malicioso |
| Filename com acentos | `Content-Disposition: attachment; filename*=UTF-8''<escaped>` |

### A06 — Vulnerable and Outdated Components

- whatsmeow: versão já usada no projeto (sem mudança).
- Nenhuma nova dependência externa adicionada (o módulo usa apenas stdlib + gorm existente + prometheus client já em uso).

### A08 — Software and Data Integrity Failures

- Escrita atômica no storage: grava em temp + `os.Rename` (evita leitor ver bytes parciais).
- Permissões: diretórios criados com `0750`, arquivos com `0640`.

### A09 — Security Logging

| Evento | Log |
|--------|-----|
| Captura de mídia bem-sucedida | `message_received` (já existia) |
| Falha de storage | `error` com tenant_id, conversation_id, message_id, size, mime |
| Download | `info` com tenant_id, file_id, media_type |
| Download com ID inexistente / outro tenant | `warn` com tenant_id, file_id |

### A10 — SSRF

Não aplicável — o módulo não faz chamadas HTTP a URLs controladas pelo usuário.

## Observações (não bloqueantes)

1. **Retention / cleanup**: não há política de expiração/deleção. Se o storage crescer sem controle, um GC manual ou feature futura precisará endereçar isso. Mitigação imediata: métrica `crm_files_stored_bytes_total` permite monitoramento.
2. **Quotas por tenant**: não há quota. Um tenant poderia encher o disco enviando muitas mídias — o teto é `FILES_MAX_BYTES` por arquivo, não por tenant. Recomenda-se abrir issue de follow-up.
3. **Download audit trail**: o log registra o download, mas não há tabela persistente de auditoria. Se requisitos regulatórios exigirem, criar `file_access_logs` em feature futura.
4. **Thumbnails sem resize**: v1 serve a imagem original. Em produção com muita banda, considerar gerar thumbnail real (S3 + lambda ou imageproxy).

## Vetores não encontrados

Foram verificados e **não há** exposição de:
- Reflected/Stored XSS: nomes de arquivo não são renderizados como HTML bruto (Go templates fazem escape automático).
- CSRF em download: o endpoint é GET idempotente; a ação de risco (escrita) não existe no módulo hoje.
- Timing oracle via 404 vs 403: handler retorna sempre 404 para recursos inexistentes ou de outro tenant.
