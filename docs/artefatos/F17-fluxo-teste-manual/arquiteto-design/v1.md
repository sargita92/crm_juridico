# F17 — Fluxo de teste manual e comando /reset

**Data**: 2026-04-13
**Status**: Design aprovado, aguardando plano de implementação

## Contexto e motivação

Hoje não conseguimos validar de ponta a ponta o caminho "lead manda mensagem → especialista IA atende → fluxo do produto é percorrido → lead qualificado" sem depender de WhatsApp real conectado via whatsmeow. A consequência é que regressões no `ConversationEngine`, no `SpecialistRouter`, nas `steps` ou nos `guardrails` só aparecem em produção.

Três gaps concretos:

1. **Fixtures incompletas**. A `fixtures.sql` seeda specialist, steps, guardrails, products e leads, mas **não seeda `ai_configs`**. O `ConfigResolver.Resolve()` cai num path de defaults hardcoded, então o caminho real de inicialização nunca é exercitado.
2. **Sem teste de integração end-to-end**. Não existe teste Go que dispare o pipeline inteiro (inbound → debouncer → router → engine → resposta → state update → lead movement) com fake provider.
3. **Sem forma de exercitar o fluxo pelo front-end sem WhatsApp real**. O handler `HandleSendMessage` atual só aceita outgoing (operador → lead). Não há como entrar no sistema como "o lead mandou algo" pela UI.

Além disso, duas pendências funcionais afetam o mesmo caminho de código:

4. **Campanhas de marketing via `wa.me/?text=...`** mandam a frase literal da URL como primeira mensagem. Precisamos que o produto tenha keywords/frases de intenção casando exatamente com essas frases pra roteamento direto. O matcher já faz substring case-insensitive, mas o `parseKeywords` do form do produto quebra em qualquer vírgula — inutilizando frases com pontuação.
5. **Reset de conversa pra testes e pra UX do lead**. Comando `/reset` digitado pelo lead zera o estado da conversa, devolvendo o fluxo ao início como se nunca tivesse mandado mensagem. Precisa ser desabilitável via env pra cenários onde não queremos expor.

## Escopo

Quatro entregas acopladas, implementadas nesta ordem:

1. **Fixture completa do fluxo IA** — seed de `ai_configs`, contato limpo pra teste, frases-exemplo nos produtos.
2. **Playground dev** — página HTMX em `/tenant/ai/playground` que injeta mensagens no pipeline real de inbound, protegida por flag `AI_PLAYGROUND_ENABLED`.
3. **`parseKeywords` CSV-aware** — respeita aspas pra permitir frases com vírgula.
4. **Comando `/reset`** — interceptado no `ConversationEngine`, controlado por `AI_RESET_COMMAND_ENABLED` (default `true`).

Suporte transversal:

- **Fake provider de IA** (`internal/ai/infrastructure/fake_provider.go`) registrado no `ProviderRegistry` com nome `"fake"`, usado por fixture de dev/test.
- **Teste de integração automatizado** em `internal/ai/application/e2e_flow_test.go` com MySQL via `testcontainers-go`, percorrendo todos os steps do especialista previdenciário.

### Fora do escopo

- Rate limiting no `/reset` (apenas documentado como risco monitorado).
- I18n da mensagem de confirmação do `/reset`.
- Mudanças no matcher de produto (`MatchesText`) — substring case-insensitive continua.
- Adaptação do ProductDetector pra usar IA/similaridade semântica.
- Conectar whatsmeow real ao playground — o playground usa o pipeline interno, não o provider WhatsApp.

### Decisão de design chave: extração do `InboundMessageUseCase`

Hoje o caminho de mensagem inbound real começa no adapter do whatsmeow, que injeta direto no debouncer e daí pro engine. Pra que "o playground" e "o WhatsApp real" exercitem exatamente o mesmo código, extraímos um usecase `InboundMessageUseCase.Execute(ctx, InboundMessageInput)` que:

1. Cria (ou encontra) a conversa e o lead pelo contato.
2. Persiste a mensagem com `direction=incoming`.
3. Empurra pro debouncer.
4. O debouncer, ao fechar a janela, chama `SpecialistRouter.Route` e então `ConversationEngine.HandleMessages`.

O adapter whatsmeow e o handler do playground ambos chamam esse usecase. Nenhuma lógica duplica.

Se o refactor for mais invasivo do que aparenta, o primeiro step do plan vai detalhar a extração como tarefa isolada com TDD próprio.

### Bloco 3 — `parseKeywords` CSV-aware

**Arquivo**: `internal/product/interfaces/http/handler.go`, função `parseKeywords`.

**Antes**:
```go
parts := strings.Split(s, ",")
```

**Depois** (usando `encoding/csv`):
```go
func parseKeywords(s string) []string {
    if strings.TrimSpace(s) == "" {
        return []string{}
    }
    r := csv.NewReader(strings.NewReader(s))
    r.LazyQuotes = true
    r.TrimLeadingSpace = true
    record, err := r.Read()
    if err != nil {
        // fallback: comportamento antigo pra não quebrar inputs válidos
        return legacyParse(s)
    }
    var result []string
    for _, p := range record {
        p = strings.TrimSpace(p)
        if p != "" {
            result = append(result, p)
        }
    }
    return result
}
```

**Template form** (`admin_product_form.html`): atualizar hint/placeholder:
> Separe por vírgula. Use aspas para frases com vírgula. Ex: `aposentadoria, "preciso revisar, é urgente"`.

**Testes**: ampliar `handler_test.go` com casos: keywords simples, keywords com frase entre aspas sem vírgula, keywords com frase entre aspas com vírgula, keywords com aspas escapadas, input vazio, input só espaços.

### Bloco 4 — Comando `/reset`

**Arquivo**: `internal/ai/application/conversation_engine.go` + novo `reset_conversation.go`.

**`ResetConversationUseCase`** (novo):

```go
type ResetConversationUseCase struct {
    stateRepo     domain.ConversationStateRepository
    leadUpdater   LeadUpdater
    leadFinder    LeadFinder     // encontra lead por conversation_id
    funnelFinder  FunnelFinder   // encontra entry column do funil default
    messageSender MessageSender
    log           *zap.Logger
}

func (uc *ResetConversationUseCase) Execute(ctx context.Context, tenantID, conversationID string) error {
    // 1. Carrega state; se não existe, cria zerado e retorna.
    // 2. state.Reset() — current_step=0, accumulated_score=0, collected_data limpo, handoff_active=false.
    // 3. stateRepo.Update(ctx, state).
    // 4. Lead ? mover pra entry column do funil default do tenant, zerar score.
    // 5. Enviar mensagem via messageSender: "Conversa reiniciada. Pode começar de novo quando quiser."
    // 6. Metric: aiResetCommandsTotal.WithLabelValues(tenantID, state.SpecialistID).Inc()
    // 7. Log info.
}
```

**Intercepção no engine** (topo de `HandleMessages`, logo após resolver/criar `state`):

```go
if e.resetCommandEnabled && isResetCommand(messages) {
    return e.resetUC.Execute(ctx, tenantID, conversationID)
}
```

`isResetCommand`: retorna true se, após `TrimSpace`, **alguma** das mensagens do batch é exatamente `/reset` (case-sensitive). Se houver outras mensagens no batch junto do `/reset`, elas são descartadas — o reset tem precedência.

**Flag**: `config.Config.AIResetCommandEnabled` (default `true`, via Viper). Passada no construtor do `ConversationEngine`.

**Métrica nova**: `ai_reset_commands_total{tenant_id,specialist_id,source}` registrada em `metrics.go`. `source` é `"command"` quando vem do engine (lead digitou `/reset`) ou `"playground"` quando vem do botão.

**Playground**: o botão "Reset" chama direto o `ResetConversationUseCase.Execute` via handler, sem passar pelo engine.

### Bloco 5 — Fake provider

**Arquivo**: `internal/ai/infrastructure/fake_provider.go` (novo).

Implementa `domain.Provider`:

```go
type FakeProvider struct {
    // opcional: script determinístico de respostas
}

func (p *FakeProvider) Name() string { return "fake" }

func (p *FakeProvider) GenerateResponse(ctx context.Context, req domain.AIRequest) (*domain.AIResponse, error) {
    // Estratégia determinística:
    // - Se é a primeira interação (sem state avançado), devolve greeting + primeira pergunta do step 0.
    // - Caso contrário, devolve a pergunta do step atual (req.CurrentStepText).
    // - Tokens prompt/completion calculados por len().
    // - Metadata do step_completed vem por rule-based (já existente), então o fake não precisa inferir.
}
```

O objetivo do fake **não** é simular IA bem — é fechar o loop. As steps avançam por regras (`StepEvaluator.EvaluateByRule`), não por metadata do LLM, então a qualidade da resposta do fake é irrelevante pro fluxo.

Registro: no wire do módulo AI, adicionar `providerRegistry.Register("fake", NewFakeProvider())` sempre (não só em dev — é barato).

### Bloco 6 — Teste de integração end-to-end

**Arquivo**: `internal/ai/application/e2e_flow_test.go` (ou `e2e_flow_integration_test.go` com build tag `integration`).

**Setup**:
- `testcontainers-go` sobe MySQL, roda migrations, carrega `fixtures.sql`.
- Wire real de todos os componentes (provider registry com fake, repos reais, engine, router, debouncer).

**Cenários cobertos**:

1. **Fluxo completo PROD_REVISAO via wa.me**: dispara mensagem `"Preciso de uma revisão na minha aposentadoria"` no contato de teste. Asserta que:
   - Especialista certo foi roteado.
   - Step 0 (nome) foi apresentado.
   - Respondendo cada step na ordem, todos avançam.
   - Score acumula.
   - Ao final, lead está qualificado e movido pra coluna `Análise Documental` (threshold 60, score total ≥ 60).
2. **`/reset` funcional**: mensagem → avança um step → manda `/reset` → asserta que state voltou pra 0, lead voltou pra `Novo Contato`, mensagem de confirmação foi enviada.
3. **`/reset` com flag desligada**: mesma coisa, mas com `AIResetCommandEnabled=false`. Asserta que `/reset` virou uma mensagem normal (provider chamado, state não zerou).
4. **Handoff ativo bloqueia engine**: se state.HandoffActive=true, mensagem entrante não chama provider.
5. **Roteamento por frase exata wa.me**: mensagem com frase-exemplo de PROD_IDADE roteia pra aquele produto, não pro PROD_REVISAO.

Testes unitários adicionais:

- `reset_conversation_test.go` — matriz de casos do usecase (state inexistente, lead inexistente, funil sem entry column, erro no repo).
- `handler_test.go` (produto) — `parseKeywords` com os casos listados no bloco 3.
- `fake_provider_test.go` — sanity check do determinismo.

## Riscos e mitigações

| Risco | Mitigação |
|---|---|
| Extração do `InboundMessageUseCase` mexe em código sensível (whatsmeow adapter) | Primeiro step do plan de implementação isola o refactor com TDD próprio antes de qualquer coisa nova |
| `/reset` em prod pode ser abusado por lead resetando score repetidamente | Monitorar métrica `ai_reset_commands_total`. Se crescer suspeitamente, adicionar rate limit (1/hora por conversa) em spec futura |
| `AI_PLAYGROUND_ENABLED=true` acidental em prod | Warning no startup + rotas só registradas quando flag on + auditoria via `ai_playground_enabled` gauge |
| Fake provider divergir do comportamento real | Nunca usado em prod. Teste de fumaça com OpenAI real antes de releases importantes |
| `parseKeywords` CSV quebra inputs antigos válidos | Fallback pro parser legacy em caso de erro do `csv.Reader` + testes cobrindo inputs antigos |

## Critérios de aceitação

1. `./scripts/refresh.sh` carrega fixture e `SELECT COUNT(*) FROM ai_configs` retorna ≥ 1.
2. Com `AI_PLAYGROUND_ENABLED=true`, acessar `/tenant/ai/playground`, selecionar contato limpo, mandar `"Preciso de uma revisão na minha aposentadoria"` e ver a resposta do especialista aparecer na tela em < 5s.
3. Percorrer todos os steps do especialista previdenciário pelo playground e ver o lead aparecer qualificado no kanban do funil.
4. Clicar em "Reset conversation" no playground zera o state; próxima mensagem começa do step 0.
5. Digitar `/reset` como mensagem no playground produz o mesmo efeito (valida o comando real).
6. Com `AI_RESET_COMMAND_ENABLED=false`, `/reset` é tratado como mensagem comum.
7. Form de produto aceita `aposentadoria, "preciso revisar, é urgente"` e salva as duas keywords separadas corretamente.
8. `go test ./internal/ai/application/... -tags=integration` passa com o cenário end-to-end completo.
9. Cobertura dos arquivos novos/alterados ≥ 80%.
10. Sem rota do playground em prod (binário buildado com `AI_PLAYGROUND_ENABLED` não setado): `curl /tenant/ai/playground` retorna 404.
