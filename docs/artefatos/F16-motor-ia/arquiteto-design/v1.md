# F16 — Motor de IA dos Especialistas — Design v1

## Objetivo

Implementar o motor de IA que permite especialistas (agentes IA) responderem automaticamente conversas do WhatsApp usando LLM, com contexto completo de treinamento (prompt, RAG, guardrails, steps, scoring) e interacao com o kanban.

## Decisoes de design

| Decisao | Escolha | Justificativa |
|---------|---------|---------------|
| Provider inicial | OpenAI (GPT-5.4-nano) | Custo baixo, boa qualidade, SDK Go disponivel |
| Config de provider | Por especialista com fallback global | Admin pode escolher provider/modelo por especialista; se nao definido, usa default do .env |
| API key | Global no .env | Simplifica v1, sem secrets no banco |
| Arquitetura | Sincrona simples | Carga baixa na v1, Go lida bem com goroutines, facil migrar para worker pool depois |
| RAG | Documentos concatenados no system prompt | Sem vector DB na v1; documentos pequenos |
| Streaming | Nao (v1) | WhatsApp nao se beneficia de streaming |
| Historico | Ultimas 20 mensagens (configuravel) | Controla tokens |
| Debounce | Configuravel por especialista (default 8s) | Agrupa mensagens curtas em sequencia |
| Avaliacao de steps | Misto: regex para dados estruturados + LLM para free_text | Economiza tokens quando possivel |
| Limites de uso | Sem limites na v1, apenas metricas | Menos complexidade agora |

## Entidades de dominio

### AIProvider (interface)

```go
type AIProvider interface {
    GenerateResponse(ctx context.Context, request AIRequest) (AIResponse, error)
    Name() string // "openai", "anthropic", etc.
}
```

### ProviderRegistry

```go
type ProviderRegistry struct {
    providers map[string]AIProvider // "openai" -> OpenAIProvider
}
func (r *ProviderRegistry) Get(name string) (AIProvider, error)
func (r *ProviderRegistry) Register(provider AIProvider)
```

Para adicionar novos providers: implementar AIProvider, registrar no bootstrap.

## Roteamento de especialista (SpecialistRouter)

Cascata de resolucao quando mensagem chega:

1. **Por numero** — `PhoneNumberRepository.FindByPhoneNumber(phone)` -> produto -> produto tem especialista vinculado? Usa esse
2. **Por produto (mensagem)** — `ProductDetector.DetectFromMessage(tenantID, text)` -> produto tem especialista? Usa esse
3. **Default** — especialista com `is_default = true` no tenant

## Context Builder

Monta o AIRequest completo a partir de todas as fontes.

### System prompt (montado em camadas, nessa ordem):

1. **Prompt base do especialista** — campo `Prompt` da entidade Specialist
2. **Produto** — nome e descricao do produto identificado
3. **Documentos RAG** — documentos do especialista via DocumentModule, concatenados
4. **Guardrails** — guardrails ativos convertidos em instrucoes explicitas
5. **Step atual** — instrucao do step corrente + tipo de dado esperado + dados ja coletados
6. **Instrucoes de formato** — pede metadata JSON para avaliacao de step (apenas free_text)

### Exemplo de system prompt montado

```
Voce e [nome do especialista]. [prompt base]

## Produto
O cliente esta interessado em: [nome do produto]. [descricao]

## Documentos de referencia
[documento 1 concatenado]
[documento 2 concatenado]

## Regras obrigatorias
- Nunca fale sobre: [topicos proibidos]
- Mantenha-se dentro do escopo: [regra de escopo]
- Tom: [regra de tom]

## Etapa atual do atendimento
Voce esta na etapa 3 de 5: "[texto do step]"
Tipo de dado esperado: [date]
Dados ja coletados: {step1: "Joao Silva", step2: "123.456.789-00"}

Quando o cliente fornecer o dado solicitado, responda normalmente e inclua ao final:
<!--STEP_META:{"step_completed":true,"collected_data":"valor","score":10}-->
```

A tag `<!--STEP_META:...-->` e extraida antes de enviar a resposta ao WhatsApp. So usada para steps free_text.

### Messages (historico)

- Ultimas N mensagens da conversa (default 20, configuravel)
- Incoming -> role "user", outgoing -> role "assistant"
- Se handoff aconteceu, so inclui mensagens com timestamp > ResumedAt
- Trunca se exceder janela de contexto (estimativa: caracteres / 4)

## Conversation Engine — fluxo principal

```
HandleIncomingMessage(ctx, tenantID, conversationID, message)
```

### Fluxo:

1. **Busca ConversationState** — se nao existe, cria (primeira interacao)
2. **Verifica handoff** — se HandoffActive == true, ignora (humano atendendo)
3. **Roteamento** — SpecialistRouter resolve qual especialista atende
4. **Debounce** — agrupa mensagens por conversa. Timer de N segundos (config do especialista). Cada mensagem nova reseta o timer. Quando timer expira, concatena mensagens e processa
5. **Context Builder** — monta AIRequest com todo o contexto
6. **Chamada ao LLM** — ProviderRegistry.Get(config.Provider).GenerateResponse()
7. **Extrai metadata** — parseia `<!--STEP_META:...-->` se presente
8. **Step Evaluator** — avalia se step foi cumprido:
   - Dados estruturados (number, date, document, selection): regex/validacao direta na mensagem do lead
   - free_text: usa metadata do LLM
   - Se cumprido: avanca CurrentStepIndex, acumula score, salva CollectedData
9. **Guardrails de saida** — verifica se resposta contem topicos proibidos (keywords dos guardrails forbidden_topics)
   - Se violou: descarta resposta, envia mensagem fallback do guardrail
   - Log de violacao para auditoria
10. **Limpa resposta** — remove tag `<!--STEP_META:...-->`
11. **Atualiza kanban**:
    - Step tem TargetColumnID? Move lead para coluna configurada
    - Todos steps completos + score >= threshold? Move para QualifiedColumnID
    - Todos steps completos + score < threshold? Move para DisqualifiedColumnID
    - Atualiza score do lead
12. **Envia via WhatsApp** — SendMessageUseCase
13. **Persiste estado** — salva ConversationState atualizado
14. **Logging** — log em cada etapa com contexto completo

## Debounce

```go
type Debouncer struct {
    timers   map[string]*time.Timer  // conversationID -> timer
    messages map[string][]string     // conversationID -> mensagens acumuladas
    mu       sync.Mutex
    callback func(conversationID string, messages []string)
}
```

Quando timer expira, concatena mensagens com `\n` e chama o engine.

## Step Evaluator

### Validacao por regra (sem gastar tokens):

| DataType | Validacao |
|----------|-----------|
| number | regex `^\d+([.,]\d+)?$` |
| date | regex para dd/mm/yyyy, dd-mm-yyyy, etc. |
| document | regex para CPF, CNPJ, RG (patterns brasileiros) |
| selection | match exato contra opcoes pre-definidas |

### Validacao por LLM (free_text):

- LLM retorna `<!--STEP_META:{"step_completed":true/false,"collected_data":"valor","score":10}-->` na resposta
- StepEvaluator parseia a tag e extrai resultado
- Se tag ausente: assume step nao cumprido, conversa continua naturalmente

### Fluxo combinado:

1. Mensagem do lead chega
2. Tenta validacao por regra primeiro
3. Se regra valida -> step cumprido, sem analise de metadata
4. Se regra nao valida ou e free_text -> LLM avalia via metadata
5. Step cumprido -> avanca index, acumula score, move coluna se configurado

## Interacao com Kanban

### Mapeamento step -> coluna (configuravel pelo admin)

Cada step pode ter um `TargetColumnID` opcional. Quando o step e cumprido e tem coluna destino, o lead move automaticamente.

Exemplos de configuracao:

| Step | Descricao | Coluna destino |
|------|-----------|---------------|
| 1 | Apresentacao | — (nao move) |
| 2 | Pedir documentos pessoais | — |
| 3 | Recebeu documentos pessoais | "Documentacao" |
| 4 | Pedir comprovante aposentadoria | — |
| 5 | Recebeu comprovante | "Analise" |
| Scoring: qualificado | | "Ganho" |
| Scoring: desqualificado | | "Perdido" |

### Regras:

- Movimentacao usa MoveLeadUseCase existente (cria LeadMovement como auditoria)
- Origem registrada como "ia" para diferenciar de movimentacoes manuais
- Produto associado ao lead na criacao (ja existe no F07)
- Score do lead sincronizado com AccumulatedScore do ConversationState

## Guardrails em runtime

### Aplicacao:

| Tipo | Enforcement | Checagem |
|------|-------------|----------|
| forbidden_topics | Pos-resposta | Scan por keywords na resposta do LLM (case-insensitive) |
| scope_limit | Prompt engineering | Instrucao no system prompt, sem checagem extra na v1 |
| response_tone | Prompt engineering | Instrucao no system prompt, sem checagem extra na v1 |

### Quando forbidden_topics viola:

1. Resposta do LLM descartada
2. Mensagem fallback do guardrail enviada ao contato
3. Log WARN de violacao
4. Metrica `ai_guardrail_violations_total` incrementada

## Handoff humano

### Assumir conversa:

- Endpoint: `POST /conversations/:id/handoff`
- Seta ConversationState.HandoffActive = true, HandoffAt = now
- Log INFO: "handoff_initiated"
- UI: botao na tela de conversa, label muda para "Atendimento manual"

### Devolver para IA:

- Endpoint: `POST /conversations/:id/handoff/release`
- Seta HandoffActive = false, ResumedAt = now
- Log INFO: "handoff_released"
- IA retoma do step onde parou
- Ignora todas as mensagens entre HandoffAt e ResumedAt
- UI: botao muda para "Devolver para IA"

### Indicador visual:

- Badge na conversa: "IA" (verde) ou "Manual" (amarelo)
- Visivel na lista de conversas e dentro do chat

### Protecao contra respostas duplicadas:

- Ao reativar IA, ResumedAt marca o momento exato
- Context Builder so inclui mensagens com timestamp > ResumedAt no historico
- IA nunca tenta responder mensagens do periodo de handoff

## Edge cases

### Especialista sem steps configurados

Se o especialista nao tem steps, o motor funciona como chatbot simples:
- Sem avaliacao de steps, sem scoring, sem movimentacao automatica de colunas
- ConversationState.CurrentStepIndex permanece 0
- O lead fica na coluna onde esta, sem movimentacoes automaticas
- ContextBuilder monta o prompt sem secao de steps

### Nenhum especialista encontrado pelo router

Se o SpecialistRouter nao encontra especialista (nenhum vinculado ao numero, nenhum ao produto, nenhum default no tenant):
- Mensagem e recebida e persistida normalmente (fluxo WhatsApp existente)
- IA nao responde
- Log WARN: "no_specialist_found" com tenant_id e conversation_id
- Lead e criado no kanban normalmente (fluxo F07 existente), sem atendimento automatico

### Lead ja existente recebe nova mensagem

- ConversationState ja existe, engine retoma do step onde parou
- Se todos os steps ja foram concluidos, IA responde como chatbot livre (sem steps)
- Nao recria lead, nao remova/recria ConversationState
