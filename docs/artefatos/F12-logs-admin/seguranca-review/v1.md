# Review de Seguranca — F12 Logs (Admin)

## Resumo executivo

**Veredito: APROVADO** sem achados de severidade alta ou critica.

A F12 entrega um modulo de auditoria global com postura solida de seguranca:

- Sanitizacao centralizada de chaves sensiveis (`SanitizeMetadata` + `IsForbiddenMetadataKey`) com lista ampliada (9 chaves cobrindo `password`, `password_hash`, `token`, `secret`, `authorization`, `hash`, `api_key`, `cookie`, `set-cookie`).
- `BuildDiff` reusa a politica do dominio (`isDiffIgnored` chama `domain.IsForbiddenMetadataKey`) — fonte unica de verdade para redaction.
- Middleware `AdminOr404` produz 404 generico identico ao caso "log inexistente" (defesa A01 — nao revela existencia).
- Queries Gorm 100% parametrizadas; `Action` validada contra enum antes de chegar ao SQL.
- Templates usam `html/template` com auto-escape; `prettyJSON` retorna `string` (nao `template.HTML`).
- Cookie de auth com `HttpOnly=true` + `SameSite=Lax` + `Secure` controlado por config.
- Logs imutaveis (sem endpoint/UI/repo method de UPDATE/DELETE) e bloqueio de auditoria nao bloqueia operacao (decisao consciente: WARN + metrica `status="error"` que F18 alerta).

## Categorias OWASP Top 10

### A01 — Broken Access Control — **PASS**

- `internal/shared/middleware/admin_or_404.go:34-66`: `AdminOr404()` redireciona com 302 para `/admin/login?return=<path>` quando claims sao nil; renderiza 404 com `audit/not_found.html` quando role != admin. Decisao bem documentada no header do arquivo (defesa A01).
- `internal/audit/interfaces/http/handler.go:90-92`: `renderNotFound` usa o MESMO template `admin/audit/not_found.html` para o caso "id inexistente" — body identico ao do middleware (S5-C08 satisfeito).
- `internal/audit/interfaces/http/handler.go:76-86`: `fetchLog` colapsa "id vazio" e "id inexistente" no mesmo retorno de erro -> mesmo 404.
- `claims.Role` unico criterio: o middleware nao consulta query/header.
- Testes: `internal/audit/interfaces/http/owasp_test.go` cobre `TestOWASP_TenantUser_*404Generic`, `TestOWASP_Admin_NonExistentID_Same404AsForbidden`, `TestAdminOr404_Unauthenticated_RedirectsToLoginWithReturn`.

### A02 — Cryptographic Failures / Sensitive Data — **PASS**

- `cmd/api/main.go:554-587`: Login publica `auth.login.success`/`auth.login.failure` enviando apenas `email`, `user_id`, `entity`, `metadata` controlado. **A senha nunca e passada ao publisher.** Verificado.
- `internal/auth/application/audit_helpers.go`: helpers `publishLoginFailure`/`publishAuthEvent` usam apenas `email` + `reason` curtos.
- `internal/audit/application/publisher_test.go`: `TestDefaultPublisher_UseCaseError_SwallowsAndLogsWarn` verifica que o WARN do Zap loga `action`/`actor_email` (sem `metadata`).
- `actor_email` e PII justificada: auditoria de seguranca tem base legal (LGPD art. 7, IX/X — exercicio regular de direito + protecao do credito/seguranca).
- JWT claim `Email` (`internal/auth/domain/token.go:7-19`): documentado como snapshot para evitar SELECT extra. Trade-off explicito; aceitavel.

### A03 — Injection — **PASS**

**SQL:**

- `internal/audit/infrastructure/gorm_audit_log_repository.go:96-108`: todas as clausulas `Where("col = ?", val)` parametrizadas. Nenhuma concatenacao.
- `internal/audit/interfaces/http/handler.go:194-200`: `Action` da querystring validada via `domain.Action(v).IsValid()` antes de virar `*Filter.Action`. Cenario S3-C23 (`action="' OR 1=1 --"`) rejeitado por enum.
- `tenant_id`/`user_id` chegam como `*string` mas o filtro usa placeholders — mesmo que mal formado, nao injeta SQL.

**XSS:**

- `cmd/api/main.go:495-501`: `prettyJSON` retorna `string` puro (`json.MarshalIndent` -> `string(b)`) — auto-escape do `html/template` se aplica. Nenhum `template.HTML` em dados de log.
- Templates `web/templates/admin/audit/*.html`: campos `{{.Log.ActorEmail}}`, `{{.Log.UserAgent}}`, `{{.Log.IP}}`, `{{deref .Log.UserID}}`, `{{prettyJSON .Log.Metadata}}` usam sintaxe padrao — auto-escape protege.
- Testes XSS: S3-C24 e S4-C16 mapeados em `qa-cenarios/v1.md` -> `internal/audit/interfaces/http/handler_test.go` cobre escape em `actor_email`/`metadata`.

**Open Redirect:**

- `internal/audit/interfaces/http/handler.go:157-161`: `ReturnURL = "/admin/logs?" + r`. Prefixo hardcoded. Mesmo que `r="https://evil.com"`, o resultado e `/admin/logs?https://evil.com` — request relativa, fica no host. NAO e open redirect.
- `<a href="{{.ReturnURL}}">` no template detail_fragment.html passa pelo auto-escape de attr URL do `html/template`. OK.

### A04 — Insecure Design — **PASS (com follow-ups)**

- **Falha de auditoria nao bloqueia operacao**: decisao consciente em `internal/audit/application/publisher.go` (`Publish` retorna nil mesmo apos erro do UC, log WARN + metric `status="error"`). Risco residual: atacante poderia provocar falhas no banco para mascarar acoes. Mitigacao: F18 alerta sobre `crm_audit_logs_registered_total{status="error"}` (recomendacao reforcada como follow-up).
- **Logs imutaveis**: `internal/audit/domain/repository.go` so expoe `Create`, `FindByID`, `List`. Sem UPDATE/DELETE em repo nem em handler. Bonus possivel: trigger MySQL `BEFORE UPDATE/DELETE` -> SIGNAL — sinalizado como follow-up.
- **Retencao ilimitada**: schema `audit_logs` nao tem `expires_at` nem cron de purga. Crescimento perpetuo pode virar DoS por disk space. Sinalizado como follow-up.

### A05 — Security Misconfiguration — **PASS**

- `migrations/000056_create_audit_logs.up.sql`: `ENGINE=InnoDB`, `CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci`. OK.
- Tamanhos: `actor_email VARCHAR(255)` (alinha com snapshot de `auth.users.email`); `user_agent VARCHAR(255)` (alinhado com `domain.MaxUserAgentLength = 255` em `audit_log.go:12` que trunca antes de chegar ao banco); `ip VARCHAR(45)` (cobre IPv6).
- Cookie `token` (`cmd/api/main.go:583-584` e `607-608`): `SameSite=Lax`, `Secure=secureCookie` (configuravel), `HttpOnly=true` (ultimo argumento `true`).

### A07 — Identification & Authentication Failures — **PASS**

- Falha de login (senha errada vs email inexistente): `cmd/api/main.go:568-572` chama `publishLoginFailure` para qualquer erro do `loginUC.Execute`, e ambos os caminhos acabam em `renderAdminLoginError` -> mesma resposta HTML "Email ou senha invalidos" + 200 com `Error` no payload (resposta identica em ambos os casos).
- Risco de timing attack pelo Publish: o publisher e sincrono mas leve (insert simples). Nao distingue email valido de invalido em ordem de microsegundos — nao explora-vel sem rede direta. Aceitavel.

### A08 — Software & Data Integrity — **PASS**

- Logs imutaveis (vide A04). Migration 56 reversivel (`down.sql` faz DROP).
- Sem dependencia nova externa (apenas zap/uuid/gorm ja usados).

### A09 — Logging & Monitoring Failures — **PASS (com follow-up)**

- Metricas Prometheus: `crm_audit_logs_registered_total{action,status}` declaradas em `internal/audit/infrastructure/metrics.go` e registradas no smoke test (`internal/shared/observability/metrics_registered_test.go`).
- Logs Zap estruturados em todas as camadas (uc/publisher/handler).
- **Follow-up**: regra de alerta dedicada para `crm_audit_logs_registered_total{status="error"} > 0` por 5min. F18 entrega regras genericas mas nao especificas para audit. Recomendado adicionar.

### A10 — SSRF — **N/A**

A F12 nao faz fetch externo.

### CSRF — **PASS**

- `/admin/logs` e `/admin/logs/:id` sao GET (sem mutacao). CSRF nao aplicavel.
- `/admin/logout` e POST mas o cookie `SameSite=Lax` mitiga CSRF cross-site basico; segue o padrao do projeto.

### XSS — **PASS**

- `prettyJSON` retorna `string` (nao `template.HTML`) — confirmado em `cmd/api/main.go:495-501`.
- Templates usam apenas `{{.Field}}` / `{{deref ...}}` / `{{prettyJSON ...}}` em dados de log. Nenhum uso de `safeHTML` ou similar.
- Testes S3-C24/S4-C16 mapeados em qa-cenarios/v1.md cobrem reflexo de payload XSS via querystring e via `actor_email`/`metadata`.

## Follow-ups (nice-to-have, nao bloqueiam merge)

1. **[A04] Trigger DB para reforcar imutabilidade**: criar trigger `BEFORE UPDATE` e `BEFORE DELETE` em `audit_logs` que faca `SIGNAL SQLSTATE '45000'`. Reforco em profundidade caso uma migration futura abra inadvertidamente uma porta de Update/Delete.
2. **[A04] Politica de retencao**: adicionar `audit_logs_retention_days` em config + cron de purga (ex.: 365 dias). Evita crescimento perpetuo. Acompanhar metric `crm_audit_logs_total_rows`.
3. **[A09] Alerta dedicado para falha de auditoria**: regra Prometheus `increase(crm_audit_logs_registered_total{status="error"}[5m]) > 0` com severidade `warning`. Adicionar a F18 ou em feature dedicada.
4. **[A05] Sanitizacao em profundidade (depth>1)**: estender `SanitizeMetadata` para descer em sub-mapas. Hoje a politica e profundidade 1; um caller mal-comportado pode passar `metadata={"ctx":{"password":"x"}}` e a chave nao seria removida. Risco baixo (callers internos sao confiaveis e auditados), mas vale para defesa em profundidade.
5. **[A07] Rate limiting em /admin/login**: nice-to-have para bloquear brute-force apos N falhas no mesmo IP/email. Hoje cada falha gera audit log -> deteccao por dashboard, mas sem bloqueio automatico.
