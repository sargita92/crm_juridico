## Premissas confirmadas no codigo atual

- IDs em todo o projeto sao **UUID v4** (`uuid.New().String()`, coluna `CHAR(36)`). Nao ha UUID v7 hoje. Mantemos o padrao.
- Existe middleware admin global: `middleware.RequireAdmin()` (`internal/shared/middleware/admin.go`) — checa `claims.Role == domain.UserRoleAdmin`. **Reutilizar.** Nao criar novo middleware.
- Existem `middleware.GetClaims(ctx)` e `middleware.GetTenantID(ctx)`; nao ha helper publico para IP/user-agent ainda — vamos criar um adapter no proprio modulo `audit`.
- O login do admin global e tratado em `cmd/api/main.go` (rota `POST /admin/login`) chamando `authMod.LoginUseCase().Execute(...)`. **Nao** ha hoje uma feature separada de "usuarios admin" — usuarios admin sao usuarios com `role = admin` gerenciados via `auth.ManageUsersUseCase`. Vamos auditar tambem operacoes do `ManageUsersUseCase` quando o ator/alvo for admin (detalhes na secao 4 e Step 7).
- `internal/shared/observability` ja expoe `StartSpan`, e cada modulo registra metricas Prometheus em `infrastructure/metrics.go` com `prometheus.MustRegister(...)` no `init()`. **Reutilizar.**
- Migrations seguem `migrations/NNNNNN_<snake>.up.sql|down.sql`. Ultima atual: `000055`. F12 usara `000056`.
- Nao existe modulo `internal/audit*` ou `internal/logs*` — feature greenfield. Tudo confirmado por busca em `internal/`, `migrations/`, `cmd/`.

## 1. Entidades e value objects

### 1.1 `AuditLog` (entidade — `internal/audit/domain/audit_log.go`)

```go
type AuditLog struct {
    ID         string    // UUID v4
    TenantID   *string   // nullable: ações sem contexto de tenant (login admin, criação de tenant)
    UserID     *string   // nullable: ator não identificado (falha de login com email inexistente)
    ActorEmail string    // snapshot legível, sobrevive à exclusão do usuário
    Action     Action    // enum tipado
    Entity     string    // "tenant" | "user_admin" | "session" | ""
    EntityID   *string   // nullable: ações que não têm entidade alvo (login)
    IP         string    // IPv4/IPv6 normalizado, max 45 chars
    UserAgent  string    // opcional, max 255 chars (truncado se vier maior)
    Metadata   Metadata  // map[string]any → JSON na persistência
    CreatedAt  time.Time // sempre UTC, formatação no UI
}
```

**Justificativa para `nullable`:**

- `TenantID`: ações como `login_success`, `login_failure`, `user_admin.created` (quando o admin global cria um usuario admin não vinculado a tenant ainda) e `tenant.created` não têm tenant pré-existente para apontar — o tenant criado pode ir em `EntityID`, não em `TenantID`. Operações **sobre** um tenant existente (block/unblock/update) preenchem `TenantID = entity_id` por consistência.
- `UserID`: falhas de login com email inexistente não conseguem identificar o ator. Preenchemos `ActorEmail` com o que foi tentado, e `UserID = nil`. OWASP/A09 exige registrar a tentativa.

## 2. Interfaces de repositorio

### 2.1 `AuditLogRepository` (`internal/audit/domain/repository.go`)

```go
type AuditLogRepository interface {
    Create(ctx context.Context, log *AuditLog) error
    List(ctx context.Context, filter AuditLogFilter, page Page) ([]*AuditLog, int64, error)
    FindByID(ctx context.Context, id string) (*AuditLog, error)

```

- **Sem** `Update` nem `Delete` — logs imutaveis (Story 2 criterio 6).
- `List` retorna total para paginacao (Wireframe Tela 1: "Mostrando 1-25 de 1.247").
- Implementacao Gorm em `internal/audit/infrastructure/gorm_audit_log_repository.go`.

### 2.2 Adapter de listagem cruzada para filtros do dropdown

A UI exibe dropdowns "Tenant" e "Usuario admin" (Wireframe Tela 1). Para nao acoplar o handler ao repo de tenants/users, criamos no handler dois listers via interfaces minimas que o composition root injeta:

```go
// internal/audit/interfaces/http/page_handler.go
type TenantLister interface {
    ListAllForFilter(ctx context.Context) ([]TenantOption, error)
}
type AdminUserLister interface {
    ListAdmins(ctx context.Context) ([]UserOption, error)
}
```

Adapters que satisfazem essas interfaces vivem em `internal/audit/infrastructure/` e delegam para `tenantMod.TenantRepo()` e `authMod.UserRepo()`.

## 3. Casos de uso (application)

### 3.1 `RegisterAuditLog` (`internal/audit/application/register_audit_log.go`)

```go
type RegisterAuditLogInput struct {
    TenantID   *string
    UserID     *string
    ActorEmail string
    Action     domain.Action
    Entity     string
    EntityID   *string
    IP         string
    UserAgent  string
    Metadata   domain.Metadata
}

type RegisterAuditLogUseCase struct {
    repo  domain.AuditLogRepository
    clock func() time.Time // injetavel para teste
    log   *zap.Logger
}

func (uc *RegisterAuditLogUseCase) Execute(ctx context.Context, in RegisterAuditLogInput) error
```

- Valida `Action.IsValid()`, `ActorEmail != ""`, `IP != ""`.
- Trunca `UserAgent` em 255 e remove chaves proibidas em `Metadata` (`password`, `password_hash`, `token`, `secret`, `api_key`, `authorization`) — defesa em profundidade contra vazamento acidental.
- **Falha do RegisterAuditLog NAO deve cancelar a operacao de negocio.** O publisher (secao 4) chama este UC mas trata o erro como WARN no log Zap, incrementa `audit_logs_registrados_total{status="error"}` e segue. Justificativa: bloquear bloqueio de tenant porque um INSERT na tabela de logs falhou e pior do que perder um registro de auditoria. Risco mitigado pela métrica de erro com alerta da F18.
- Span: `audit.usecase.register`. Atributos: `audit.action`, `audit.tenant_id`, `audit.actor_email`.

## 4. Integracao com features existentes (estrategia de captura)

### 4.1 Decisao: Publisher injetavel (em vez de middleware HTTP puro)

Eventos auditaveis nao sao 1:1 com requests (ex.: numa mesma request POST `/admin/tenants/:id` o ato auditado e "atualizar tenant", e nao "fez um POST"). Alem disso, a captura precisa do **input estruturado** (motivo de bloqueio, diff de campos, papel antes/depois) que so o caso de uso conhece.

**Solucao:** interface `AuditPublisher` exposta pelo `audit.Module` e injetada nos casos de uso que produzem eventos auditaveis.

```go
// internal/audit/application/publisher.go
type AuditPublisher interface {
    Publish(ctx context.Context, in RegisterAuditLogInput)
}

// Implementacao default: chama RegisterAuditLogUseCase e ignora erro (loga WARN).
type defaultPublisher struct {
    uc  *RegisterAuditLogUseCase
    log *zap.Logger
}
```

### 4.2 Captura de IP e User-Agent

Helper novo em `internal/shared/middleware/request_meta.go`:

```go
type requestMetaKey struct{}

type RequestMeta struct {
    IP        string
    UserAgent string
}

func RequestMeta(c *gin.Context) gin.HandlerFunc { /* injeta no ctx */ }
func GetRequestMeta(ctx context.Context) RequestMeta
```

- IP via `c.ClientIP()` (Gin ja respeita `X-Forwarded-For` configurado).
- UA via `c.Request.UserAgent()` truncado em 255.
- Middleware aplicado **globalmente** no router — custo desprezivel.
- Os casos de uso leem com `middleware.GetRequestMeta(ctx)` e passam para `Publish`.

### 4.3 Mapa de eventos auditaveis

| Origem (modulo / use case)                            | Action                          | Entity        | EntityID            | TenantID                | Metadata                                                                 |
|--------------------------------------------------------|---------------------------------|---------------|---------------------|-------------------------|--------------------------------------------------------------------------|
| `auth.LoginUseCase` (sucesso, em `cmd/api/main.go` rota `POST /admin/login`) | `login.success`                 | `session`     | nil                 | nil                     | `{}`                                                                     |
| `auth.LoginUseCase` (erro)                             | `login.failure`                 | `session`     | nil                 | nil                     | `{"reason": "invalid_credentials" | "user_blocked"}`, `actor_email = email tentado` |
| logout (rota existente)                                | `logout`                        | `session`     | nil                 | nil                     | `{}`                                                                     |
| `tenant.CreateTenantUseCase`                           | `tenant.created`                | `tenant`      | novo id             | novo id                 | `{"name": "...", "type": "PJ"}`                                          |
| `tenant.UpdateTenantUseCase`                           | `tenant.updated`                | `tenant`      | id                  | id                      | `{"fields": {...diff...}}` (via `BuildDiff`)                             |
| `tenant.DeactivateTenantUseCase`                       | `tenant.deactivated`            | `tenant`      | id                  | id                      | `{}`                                                                     |
| `tenant.BlockTenantUseCase`                            | `tenant.blocked`                | `tenant`      | id                  | id                      | `{"reason": "..."}`                                                      |
| `tenant.UnblockTenantUseCase`                          | `tenant.unblocked`              | `tenant`      | id                  | id                      | `{"reason": "..."}`                                                      |
| `auth.ManageUsersUseCase` (criacao de admin)           | `user_admin.created`            | `user_admin`  | id do user          | nil                     | `{"name": "...", "email": "..."}`                                        |
| `auth.ManageUsersUseCase` (update de admin)            | `user_admin.updated`            | `user_admin`  | id                  | nil                     | `{"fields": {...diff...}}`                                               |
| `auth.ManageUsersUseCase` (desativacao/bloqueio)       | `user_admin.deactivated/blocked/unblocked` | `user_admin` | id        | nil                     | `{"reason": "..."}` (quando aplicavel)                                   |
| `permission.ManagePermissionsUseCase` (alteracao de papel/grupo/perfil de usuario admin) | `permission.changed`           | `user_admin`  | id do user alvo     | tenant alvo se houver   | `{"role": {"before": "operador", "after": "gestor"}, "group": {...}, "view_profile": {...}}` |

**Cuidado**: `permission.changed` so sera registrado quando o **alvo** for um usuario admin (`role = admin`). Alteracoes de permissao de usuarios de tenant ficam fora do escopo do MVP (PO Story 1, "Nao entra: CRUD operacional do tenant").

### 4.4 Onde colar o `publisher.Publish(...)`

- **Apos** a persistencia bem sucedida (commit). Nunca antes — auditar uma operacao que falhou e ruido.
- **Dentro** do caso de uso (nao no handler) — caso de uso e o unico lugar que conhece o input estruturado.
- Para login: como hoje o login do admin acontece em `cmd/api/main.go` chamando direto `loginUC.Execute`, o `Publish` ficara naquele bloco (decoracao do handler), passando `actor_email = email do form`. O caso de uso `LoginUseCase` continua puro.

Exemplo (pseudo-codigo do `BlockTenantUseCase` apos modificacao):

```go
if err := uc.repo.Update(ctx, tenant); err != nil { return err }
if err := uc.historyRepo.Save(ctx, entry); err != nil { return err }

meta := middleware.GetRequestMeta(ctx)
uc.publisher.Publish(ctx, application.RegisterAuditLogInput{
    TenantID:   &input.ID,
    UserID:     &input.PerformedBy,
    ActorEmail: middleware.GetClaims(ctx).Email, // claims hoje nao tem email — ver 4.5
    Action:     auditdomain.ActionTenantBlocked,
    Entity:     "tenant", EntityID: &input.ID,
    IP: meta.IP, UserAgent: meta.UserAgent,
    Metadata: auditdomain.Metadata{"reason": input.Reason},
})
return nil
```

### 4.5 `ActorEmail` nas claims

Hoje `domain.TokenClaims` tem `UserID`, `Role`, `TenantID` — **nao tem email**. Opcoes:

1. Adicionar `Email` em `TokenClaims` (preferida — barato, JWT cresce ~50 bytes).
2. Cada caso de uso busca o user por id antes de publicar (custo extra de SELECT).

**Decisao:** opcao 1. Inclui-se no Step 5 a alteracao em `auth.LoginUseCase` para popular o claim e em `infrastructure.JWTProvider` para serializar/deserializar. Ja sai pronto para a F12.

### 4.6 Falha de login

O fluxo de admin login hoje (`cmd/api/main.go`) so sabe que houve `err`. Para diferenciar `invalid_credentials` de `user_blocked`, o `LoginUseCase` ja retorna erros tipados (`ErrInvalidCredentials`, `ErrUserBlocked`). O bloco do handler mapeia o erro para `metadata.reason` antes de publicar:

```go
output, err := loginUC.Execute(ctx, ...)
if err != nil {
    publisher.Publish(ctx, RegisterAuditLogInput{
        ActorEmail: email, // do form
        Action:     auditdomain.ActionLoginFailure,
        Entity:     "session",
        IP: meta.IP, UserAgent: meta.UserAgent,
        Metadata: auditdomain.Metadata{"reason": classifyLoginErr(err)},
    })
    renderAdminLoginError(c); return
}
```

## 5. Contratos HTTP

Pacote `internal/audit/interfaces/http/`. Dois handlers: `Handler` (rotas funcionais) e `PageHandler` (rotas que renderizam HTML — padrao do projeto).

### 5.1 `GET /admin/logs`

- Query string: `tenant_id`, `user_id`, `action`, `from` (YYYY-MM-DD), `to` (YYYY-MM-DD), `page` (>=1), `page_size` (10/25/50/100).
- **Sem** header `HX-Request` → renderiza `audit/list.html` (layout `base.html`/sidebar admin completa).
- **Com** header `HX-Request: true` → renderiza fragmento `audit/list_table.html` (tbody + paginacao + contagem) com `hx-target="#logs-list"` e `hx-push-url="true"` na origem do request.
- 200 sempre que autorizado; tabela vazia tem template proprio.

### 5.2 `GET /admin/logs/:id`

- Renderiza `audit/detail.html` (full page) ou fragment `audit/detail_fragment.html` se `HX-Request: true`.
- Aceita `?return=<base64 da querystring>` — preserva filtros para "Voltar para listagem" (Wireframe Tela 2 / Decisao UI/UX 6).
- 404 quando `domain.ErrAuditLogNotFound` (template `audit/not_found.html`).

### 5.3 `GET /admin/logs/filters/tenants` e `GET /admin/logs/filters/users` (opcional, fragmento HTMX)

Wireframe sugere dropdowns "searchable" para >100 tenants/users. Endpoints retornam `<option>`s renderizados a partir do `q` da query string (`hx-get`). Nao bloqueiam o MVP — pode ficar para Step 8 ou ser substituido por `<select>` nativo no primeiro release.

### 5.4 Autorizacao e 404 generico

Todas as rotas vivem dentro de `router.Group("/admin/logs", mw.Auth, mw.Admin, ...)`.

- **Nao autenticado** → `mw.Auth` retorna 401 JSON. Para a UI HTMX o `hx-boost`/handler do front converte em redirect para `/admin/login`. Manter padrao do `/admin/dashboard` atual.
- **Autenticado nao-admin** → o middleware `mw.Admin` hoje retorna **403** (`{"error":"admin access required"}`). A Story 5 criterio 4 exige **404 generico**. Solucao: criar variante `mw.AdminOr404()` apenas para o grupo `/admin/logs` que retorna 404 com `audit/not_found.html`. Reaproveita `RequireAdmin` mudando so o status code e o body; arquivo `internal/shared/middleware/admin_or_404.go`. Nao mudamos o `RequireAdmin` existente (compatibilidade com outras telas admin que ja respondem 403).

## 6. Migrations

### 6.1 `000056_create_audit_logs.up.sql`

```sql
CREATE TABLE IF NOT EXISTS audit_logs (
    id           CHAR(36)     NOT NULL,
    tenant_id    CHAR(36)     NULL,
    user_id      CHAR(36)     NULL,
    actor_email  VARCHAR(255) NOT NULL,
    action       VARCHAR(64)  NOT NULL,
    entity       VARCHAR(64)  NOT NULL DEFAULT '',
    entity_id    CHAR(36)     NULL,
    ip           VARCHAR(45)  NOT NULL,                  -- IPv6 compativel
    user_agent   VARCHAR(255) NOT NULL DEFAULT '',
    metadata     JSON         NULL,
    created_at   TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),

    PRIMARY KEY (id),
    INDEX idx_audit_created_at        (created_at DESC),
    INDEX idx_audit_tenant_created    (tenant_id, created_at DESC),
    INDEX idx_audit_user_created      (user_id, created_at DESC),
    INDEX idx_audit_action_created    (action, created_at DESC)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

- **Sem FK** para `tenants`/`users`. Audit log precisa sobreviver a deletes (e o usuario pode ser hard-deleted no futuro). `actor_email` e o snapshot legivel.
- `created_at` com precisao de milissegundos para ordenar consistentemente em rajadas (ex.: bloqueio em massa).
- **Trade-off de indices vs inserts**: 4 indices secundarios em uma tabela de muita escrita aumentam custo de INSERT (~10-20% por indice). Aceitavel porque (a) audit_logs nao e write-hot path em MVP — admin/seguranca tem volume baixo (estimativa: <10 mil/dia), (b) UX da listagem com filtros precisa dos 4 acessos. Caso o volume cresca em features futuras (auditoria operacional do tenant), revisar — possivelmente usando particionamento por mes ou `INDEX (created_at) INCLUDE (...)`-like com tabela secundaria. Fora do MVP.

### 6.2 `000056_create_audit_logs.down.sql`

```sql
DROP TABLE IF EXISTS audit_logs;
```

## 7. Composition root / mini DI (`cmd/api/main.go`)

Ordem de wiring (apenas trecho novo, mantendo o resto):

```go
// 1. Apos os modulos existentes, criar audit module:
auditMod := audit.NewModule(db, log)

// 2. Criar publisher (decora UC + log):
auditPublisher := auditMod.Publisher() // já loga warn em erro

// 3. Injetar publisher nos modulos que auditam:
tenantMod.SetAuditPublisher(auditPublisher)
authMod.SetAuditPublisher(auditPublisher)
permissionMod.SetAuditPublisher(auditPublisher)

// 4. Adapter de filtros para a UI:
tenantLister := auditinfra.NewTenantListerAdapter(tenantMod.TenantRepo())
adminUserLister := auditinfra.NewAdminUserListerAdapter(authinfra.NewGormUserRepository(db))
auditMod.AttachFilters(tenantLister, adminUserLister)

// 5. Registrar audit no slice de modulos:
modules = append(modules, auditMod)

// 6. Middleware global novo:
router.Use(middleware.RequestMeta())
```

`audit.Module` (`internal/audit/module.go`) fornece:

- `RegisterAuditLogUseCase`, `ListAuditLogsUseCase`, `GetAuditLogUseCase`.
- `Publisher() AuditPublisher`.
- `Name() string` e `RegisterRoutes(r, mw)` (interface `module.Module`) — registra `/admin/logs*` usando `mw.Auth` + `mw.AdminOr404` (novo middleware).

## 9. Observabilidade

### 9.1 Metricas (`internal/audit/infrastructure/metrics.go`)


## 10. Seguranca

1. **Autorizacao**: somente admin global. Reuso de `mw.Auth` + variante `mw.AdminOr404` (404 generico, OWASP A01 — Story 5 criterio 4).
2. **Sanitizacao** no `RegisterAuditLog`:
   - `UserAgent` truncado em 255 caracteres, removendo control chars (`\r\n\t` viraria `replace ' '`).
   - `IP` validado: aceita formato IPv4/IPv6 valido (regex ou `net.ParseIP`); senao registra como `"invalid"`.
3. **Chaves proibidas em `Metadata`** (helper `domain.SanitizeMetadata`):
   ```go
   var forbiddenKeys = map[string]struct{}{
       "password": {}, "password_hash": {}, "token": {}, "secret": {},
       "api_key": {}, "authorization": {}, "cookie": {}, "set-cookie": {},
   }
   ```
   Aplicado tanto em `RegisterAuditLog.Execute` quanto em `BuildDiff` (defesa em profundidade — se o caller esquecer, o sanitizer remove).
4. **CSRF**: as rotas `/admin/logs*` sao GET — sem CSRF necessario. Se no futuro houver POST (ex.: salvar filtros), seguir o middleware CSRF padrao do projeto.
5. **OWASP A09 (Security Logging)**: o proprio fato dessa feature existir cobre A09. Falhas de login geram log com `actor_email` e `reason`. Tentativa de acesso negado a `/admin/logs` por usuario nao-admin **opcionalmente** (Story 5 criterio 5) gera `audit_log` com `action="access_denied"` — fora do enum atual; **decisao:** nao incluir no MVP (criterio diz "podem"). Adicionar se Seguranca pedir no review.
6. **Tenant isolation**: como apenas admin global ve a tabela, nao ha multi-tenant scope. O filtro `tenant_id` na UI e **filtro de leitura**, nao de seguranca.

## Resumo do design

- **Modulo greenfield** `internal/audit/` com Clean Architecture (domain / application / infrastructure / interfaces/http).
- **Captura via publisher** injetado nos casos de uso de auth/tenant/permission — nao via middleware HTTP, porque o conteudo auditado depende do input do dominio (motivo, diff, papel).
- **Imutavel** (sem update/delete), **retencao ilimitada**, **somente admin global** com 404 generico para nao-admin.
- **UUID v4** alinhado ao restante do projeto, JSON em `metadata`, 4 indices alinhados aos filtros do wireframe.
- **TokenClaims ganha `Email`** — mudanca pequena no auth, viabiliza `actor_email` sem SELECT extra.
- **Falha de auditoria nao quebra a operacao** — `Publish` ignora erro com WARN + metric `status="error"` para a F18 alertar.
- **10 steps atomicos**, cada um com criterio de pronto e cobertura >= 80%.
