# Wireframes e Fluxos — F12 Logs (Admin)

## Principio geral

Logs de auditoria sao uma ferramenta de **investigacao** usada pelo admin global em monitor grande (priorizar desktop). A experiencia precisa ser densa em informacao mas clara: muitos registros listados de forma escaneavel, filtros sempre visiveis, detalhe focado em "o que aconteceu" sem JSON cru. Nada visivel ou descobrivel para usuarios de tenant. Toda interacao via HTMX, sem SPA.

Materializa as Stories 1 a 5 do PO (`po-stories/v1.md`):
- Story 1 e 2 sao backend/persistencia — visualmente refletidas no detalhe do log.
- Story 3 → tela de listagem com filtros.
- Story 4 → tela de detalhe.
- Story 5 → estado de acesso negado e blindagem das rotas `/admin/logs/...`.

---

## Fluxo de navegacao

```
Sidebar Admin (header global)
  └── Logs            → /admin/logs                         (nova entrada)
        ├── filtros (tenant, usuario, acao, periodo)
        ├── tabela paginada (linha clicavel)
        │     └── clique linha → /admin/logs/:id
        │             ├── cabecalho da acao
        │             ├── "O que aconteceu"
        │             ├── "Contexto" (entidade, tenant, IP)
        │             ├── "Dados adicionais" (diff / motivo)
        │             └── botao "Voltar para listagem" (preserva filtros via querystring)
        ├── pagina vazia (sem registros / filtro sem resultado)
        ├── pagina de erro (falha ao carregar)
        └── tentativa de acesso por usuario tenant → 404/403 generico

URLs:
  /admin/logs                      → listagem (parametros: tenant_id, user_id, action, from, to, page, page_size)
  /admin/logs/:id                  → detalhe (preserva ?return=<querystring> para voltar)
  /admin/logs/:id/fragment         → mesmo detalhe em fragmento HTMX (modal opcional)
```

Sem rotas equivalentes na area do tenant. Qualquer tentativa de chamar `/admin/logs*` autenticado como tenant retorna a pagina generica "Pagina nao encontrada ou acesso negado" (vide secao Story 5).

### Componentes

#### Bloco de filtros (sempre visivel, acima da tabela)

- **Tenant**: dropdown searchable (HTMX `hx-get="/admin/logs/filters/tenants?q=:term"` opcional para >100 tenants; padrao "Todos").
- **Usuario**: dropdown searchable de usuarios admin (mesmo padrao).
- **Acao**: dropdown com tipos enumerados:
  - Login (sucesso) / Login (falha) / Logout
  - Tenant criado / Tenant editado / Tenant desativado / Tenant bloqueado / Tenant desbloqueado
  - Usuario admin criado / Usuario admin editado / Usuario admin desativado / Usuario admin bloqueado / Usuario admin desbloqueado
  - Permissao alterada
- **Periodo**: dois `<input type="date">` nativos do browser (sem JS custom — justificativa: cobre 100% dos browsers modernos, evita libs externas e mantem acessibilidade). Padrao: ultimos 7 dias.
- **Botao "Aplicar"**: submete o form via HTMX:
  - `hx-get="/admin/logs"` `hx-target="#logs-list"` `hx-push-url="true"` `hx-indicator="#logs-loading"`
- **Botao "Limpar filtros"**: link para `/admin/logs` (sem querystring). Posicao: ao lado de "Aplicar", a esquerda — escolhi colocar dentro do bloco de filtros porque limpar e parte do mesmo gesto mental de "ajustar filtro"; nao virar acao secundaria perdida no header.

> Observacao de UX: nao usar `hx-trigger="change"` em cada campo — o admin costuma ajustar varios filtros de uma vez, e disparar request a cada change inunda backend e gera flicker. Aplicar com botao explicito.

#### Tabela paginada

- Colunas (desktop): **Data/hora** (com fuso, ex: `24/04 14:32:10 BRT`), **Ator** (e-mail), **Acao** (rotulo humanizado), **Entidade** (tipo + id curto, ex: `Tenant #42`), **IP** (truncado, ex: `200.x.x.1`, hover mostra completo via `title`).
- Linha clicavel (toda a `<tr>` virou link): `hx-get="/admin/logs/:id?return=<querystring atual>"` `hx-target="#main-content"` `hx-push-url="true"`. Cursor pointer, hover com fundo cinza claro.
- Sem botao "ver detalhe" extra na linha — economia de espaco e o clique na linha ja resolve. Aria: `<a href="/admin/logs/:id?return=...">` real (progressive enhancement) envolvendo cada linha em wrapper acessivel.
- Sem botoes de editar/excluir (logs imutaveis).

#### Contagem e paginacao

- Topo: `Mostrando X-Y de N registros` (texto pequeno, alinhado a esquerda).
- Rodape: paginacao compacta com `« anterior`, `Pagina N de M`, `proxima »`, e seletor de page size (10/25/50/100).
- HTMX: cada link de pagina e `hx-get="/admin/logs?...&page=N"` `hx-target="#logs-list"` `hx-push-url="true"`.

### Estados

- **Carregando** (primeiro load ou aplicar filtro):
  - Skeleton de 8 linhas com blocos cinzas animados.
  - `<div id="logs-loading" class="htmx-indicator">` com spinner pequeno proximo ao botao "Aplicar".
- **Com dados**: tabela renderizada normalmente.
- **Vazio (sem registros no banco)** — improvavel mas possivel em primeiro deploy:
  - Icone neutro + texto: "Nenhum log registrado ainda. Acoes de administracao aparecerao aqui."
- **Vazio (filtro sem resultado)**:
  - Texto: "Nenhum log encontrado para os filtros aplicados."
  - Botao "Limpar filtros" em destaque.
- **Erro ao carregar**:
  - Texto: "Nao foi possivel carregar os logs. Tente novamente."
  - Botao "Tentar novamente" (`hx-get` na URL atual).

### Atalhos e usabilidade

- Tecla `/` foca o primeiro filtro (tenant) — comum em paineis de admin.
- `Esc` dentro de qualquer dropdown searchable fecha o dropdown.
- Datas com placeholder `dd/mm/aaaa` (input nativo cuida do mask).
- Tooltip no IP completo via atributo `title` (HTML puro, sem JS).
- Mensagens de erro em portugues claro, sem stack trace.

### Responsividade

- **Desktop (>= 1024px)**: layout descrito acima, todas as 5 colunas visiveis.
- **Tablet (768-1023px)**: bloco de filtros vira 2 colunas (4 filtros em 2x2). Tabela mantem todas as colunas mas com fonte menor (13px).
- **Mobile (< 768px)**:
  - Filtros viram um botao "Filtros (3 ativos)" que abre um drawer/modal HTMX (`hx-get="/admin/logs/filters/panel"`). Justificativa: 4 filtros em tela mobile estouram a tela; drawer e o padrao usado tambem na F07.
  - Tabela vira **lista de cartoes** (escolha consciente sobre scroll horizontal — cartao e mais legivel num celular e o admin raramente usa logs no celular; quando usa, esta no transporte e quer escanear rapido). Cada cartao:
  ```
  ┌─────────────────────────────────────┐
  │ Tenant bloqueado                    │
  │ por admin@crm.com                   │
  │ Tenant #42 · IP 200.x.x.1           │
  │ 24/04 14:32:10                      │
  └─────────────────────────────────────┘
  ```
  - Cartao inteiro clicavel (mesmo destino).

### Componentes

- **Breadcrumb / "Voltar para listagem"**:
  - Link `← Voltar para listagem`. Destino: `/admin/logs?<querystring preservada via parametro return>`.
  - Implementacao: a listagem injeta `?return=<base64 da querystring>` ao navegar para o detalhe; o detalhe decodifica e usa no link voltar. Alternativa: ler `Referer` (mais simples, mas menos confiavel apos refresh). Decisao: usar querystring `return` para garantir reproducibilidade.
- **Cabecalho da acao**: card com nome humanizado da acao (titulo grande), data/hora absoluta com fuso, ator, e id curto do log no canto direito (util para suporte).
- **Bloco "O que aconteceu"**: paragrafo em portugues natural (gerado backend a partir do tipo de acao + parametros). Ex: "O administrador X criou o tenant Y", "O administrador X tentou login sem sucesso".
- **Bloco "Contexto"**: lista chave-valor com **Entidade afetada**, **Tenant relacionado** (so aparece se aplicavel), **IP**, **Data/hora**.
- **Bloco "Dados adicionais"**: renderiza conforme tipo de acao:
  - **Bloqueio/desbloqueio**: card com texto "Motivo do bloqueio" + corpo do motivo (textarea readonly visualmente).
  - **Edicao**: tabela 3 colunas (Campo / Antes / Depois). Decisao: tabela em vez de pares "campo: antes → depois" inline porque com 5+ campos a leitura de tabela e muito superior. Em telas estreitas a tabela vira lista vertical (ver responsividade).
  - **Permissao alterada**: bloco com tres linhas (papel / grupo / perfil) usando seta unicode `→` entre antes e depois.
  - **Login (falha)**: campo extra "E-mail tentado" + texto "Senha invalida" (sem expor mais detalhe — Story 5).
  - **Criacao / desativacao / login sucesso**: bloco "Sem dados adicionais" (texto cinza claro), evitando vazio confuso.
- **Imutabilidade**: nenhum botao "Editar" ou "Excluir" em lugar nenhum. Story 4 criterio 5.

### Estados

- **Carregando**: skeleton de 4 blocos retangulares.
- **OK**: renderizacao normal.
- **Log nao encontrado** (id invalido): tela "Log nao encontrado" + botao "Voltar para listagem". Resposta HTTP 404.
- **Erro de carregamento**: "Nao foi possivel carregar este log" + "Tentar novamente".

### Interacoes HTMX

- Acesso direto via URL ou via clique na linha da listagem.
- Botao "Voltar": `<a href="/admin/logs?...">` com `hx-boost="true"` para manter SPA-like sem ser SPA.
- Sem modais — tela cheia para nao perder contexto durante investigacao.

### Responsividade

- **Desktop**: layout em uma coluna larga centralizada (max-width 960px) para legibilidade.
- **Tablet**: idem, max-width adaptado.
- **Mobile**:
  - Tabela de diff (Antes/Depois) vira lista vertical:
    ```
    Campo: Nome
      Antes:  Escritorio Silva
      Depois: Escritorio Silva & Cia
    ```
  - Blocos empilham, fonte 14px, padding reduzido.
  - Botao "Voltar" no topo, fixo (sticky).

## Tela 3: Acesso negado (Story 5)

### Comportamento

Usuario autenticado **sem ser admin global** que tente acessar `/admin/logs` ou `/admin/logs/:id`:

- Backend retorna **404 com pagina generica** (decisao explicita — Story 5 criterio 4: "nao revelar existencia da rota"). Nao usar 403 com mensagem "voce nao tem permissao para ver logs", pois isso confirma a existencia do recurso.
- Tela exibida: a mesma pagina 404 padrao do sistema, com mensagem:

```
┌──────────────────────────────────────────────────────────────────────────┐
│                                                                          │
│                          Pagina nao encontrada                           │
│                                                                          │
│   A pagina que voce tentou acessar nao existe ou voce nao tem permissao  │
│   para visualiza-la.                                                     │
│                                                                          │
│                       [Voltar para o inicio]                             │
│                                                                          │
└──────────────────────────────────────────────────────────────────────────┘
```

- Texto deliberadamente ambiguo ("nao existe **ou** voce nao tem permissao") — cobre os dois casos sem confirmar nenhum.

Usuario **nao autenticado**:
- Redirect 302 para `/login?next=/admin/logs[/:id]` (mesmo padrao das demais rotas admin existentes em F02/F03). O `next` so e seguido se, apos login, o usuario for admin global; caso contrario cai no fluxo 404 acima.

### Log de tentativa (opcional, ja previsto na Story 5 criterio 5)

- Tentativa de acesso negado por nao-admin pode gerar um log proprio do tipo "Tentativa de acesso negado" (decisao do Arquiteto/Backend). Visualmente nada muda na tela negada.

## Padroes transversais

### HTMX

- Listagem e paginacao: `hx-get` com `hx-target="#logs-list"` e `hx-push-url="true"`.
- Filtros: submit do form com `hx-get="/admin/logs"` (GET com querystring para ser bookmarkavel/compartilhavel).
- Indicadores de carregamento: `hx-indicator="#logs-loading"` em cada acao significativa.
- Detalhe: navegacao normal com `hx-boost` para preservar layout sem JS.
- Sem JS custom — apenas inputs nativos do browser (date pickers).

### Acessibilidade

- Tabela com `<thead>` e `<th scope="col">`.
- Linhas como `<a>` envolvendo a `<tr>` (ou `role="link"` + `tabindex="0"`).
- Filtros com `<label for>` explicito, sem placeholder-only.
- Foco visivel em todos os elementos interativos.
- Mensagens de erro com `role="alert"`.

### Mensagens

- Tudo em portugues do Brasil, tom neutro/profissional (e uma tela de auditoria, nao de marketing).
- Nunca expor detalhes tecnicos (stack trace, IDs internos longos) na UI.
- Datas: sempre com fuso visivel para evitar ambiguidade (Story 2 criterio 7).

### Skeleton loading

- Listagem: 8 linhas de skeleton com 5 blocos cinzas (combinando com as 5 colunas).
- Detalhe: 4 cards de skeleton retangulares.

## Decisoes registradas

1. **Filtros com submit explicito (botao Aplicar)** em vez de auto-submit por change — evita carga no backend e flicker durante ajuste de varios filtros.
2. **Botao "Limpar filtros" dentro do bloco de filtros**, ao lado de "Aplicar" — mesmo gesto mental de ajuste de filtro.
3. **Date pickers nativos do browser** — unica concessao a "JS custom"; e `<input type="date">` puro, suportado em 100% dos browsers modernos. Sem libs externas.
4. **Mobile: cartoes em vez de scroll horizontal** — admin raramente usa logs no celular; quando usa, escaneabilidade > densidade. Mantem consistencia com F07/F08 que ja usam cartoes em mobile.
5. **Diff em tabela 3 colunas (Campo/Antes/Depois)** em vez de inline com setas — superior para 5+ campos. Em mobile vira lista vertical.
6. **Voltar preserva filtros via querystring `return=`** em vez de `Referer` — sobrevive a refresh e e compartilhavel.
7. **404 generico para acesso nao autorizado** (em vez de 403 com mensagem "sem permissao") — atende criterio OWASP da Story 5: nao confirma a existencia da rota.
8. **Sem botoes de editar/excluir em nenhuma tela** — logs imutaveis (Stories 2 e 4).
9. **Texto humanizado em "O que aconteceu"** — nada de JSON cru (Story 4 criterio explicito).
10. **Paginacao server-side com page size selecionavel** (10/25/50/100) — permite ao admin balancear densidade vs scroll.
